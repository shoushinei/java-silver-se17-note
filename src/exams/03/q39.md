シールクラスとシールインタフェースについての説明として、正しいものを選びなさい。

- A. permits 句は、どのような場合でも省略できない
- B. permits に書いたクラスは、そのシールクラスを直接継承していなければならない
- C. シールインタフェースを実装するクラスにも、final・sealed・non-sealed のどれかを付ける必要がある（record は暗黙に final なので付けなくてよい）
- D. abstract を付けたクラスは、sealed にできない
- E. non-sealed を付けたクラスを継承するクラスにも、final・sealed・non-sealed のどれかを付ける必要がある
- F. シールクラスのサブクラスは、すべてシールクラスと同じソースファイルに書かなければならない

## 解説
- A: 誤り。サブクラスを**同じソースファイル**に書いた場合は、permits を省略できます。そのファイルの中のサブクラスが、許可されたものとして扱われます。
- B: 正しい。permits に名前を書いておきながら、そのクラスが継承していない（`extends` が無い）とコンパイルエラーです。
- C: 正しい。シールクラスの子と同じく、シールインタフェースを実装するクラスにも、final・sealed・non-sealed のどれかが必要です。record は暗黙に final なので、何も書かなくても条件を満たします。
- D: 誤り。`public abstract sealed class Shape permits ...` のように組み合わせられます。sealed で子を限定し、abstract で親自身の new を禁止する、よくある組み合わせです。
- E: 誤り。non-sealed は「ここから先は制限なし」という意味です。その子は、ふつうのクラスと同じように修飾子なしで書けます。
- F: 誤り。permits に書けば、同じパッケージ（名前の無いモジュールの場合）の別のファイルに書けます。同じファイルにまとめる必要があるのは、permits を省略するときです。

## 検証
@case 正解 B: permits に書いたのに継承していないと CE
@file Shape.java
sealed class Shape permits Circle { }
final class Circle { }
@javac-error

@case 正解 C: 修飾子の無い実装クラスは CE
@file Shape.java
sealed interface Shape permits Circle { }
class Circle implements Shape { }
@javac-error

@case 正解 C: record なら修飾子なしで OK
@file Shape.java
sealed interface Shape permits Circle { }
record Circle(double r) implements Shape { }
@javac

@case A・D は誤り: 同じファイルなら permits を省略でき、abstract と組み合わせられる
@file Shape.java
abstract sealed class Shape { }
final class Circle extends Shape { }
@javac

@case E は誤り: non-sealed の子は修飾子なしで書ける
@file Shape.java
sealed class Shape permits Circle { }
non-sealed class Circle extends Shape { }
class SmallCircle extends Circle { }
@javac

@case F は誤り: 別のファイルに書ける
@file Shape.java
public sealed class Shape permits Circle { }
@file Circle.java
public final class Circle extends Shape { }
@javac

アクセス修飾子と継承 ── 総まとめ

アクセス修飾子そのものは第1章 07 で扱いました。ここでは継承と組み合わさったとき、特に親と子でパッケージが違うときに何が起きるかをまとめます。以下の例は、親 lib.Parent と子 app.Child が別のパッケージにある前提です。

以下の説明で使う親クラス前提
package lib;

public class Parent {
    public    void pub()  { }
    protected void prot() { }
              void pkg()  { }   // 修飾子なし
    private   void priv() { }
}

全体像

修飾子同じパッケージの子に
継承されるか		別パッケージの子に
継承されるか		別パッケージの子の中で
this / super 経由		別パッケージの子の中で
親の型の参照経由
public○○○○
protected○○○×
なし○×××
private××××

「継承される」とは、子のメンバとして持てて、オーバーライドできるという意味です。継承されないメンバは、子に同じ名前のメソッドを書いても別物の新しいメソッドになり、@Override を付けるとコンパイルエラーです。

同じパッケージの中なら、private 以外はすべてパッケージの権限だけで届きます。表がややこしくなるのはパッケージが違うときだけで、その中心にいるのが protected です。

1. private は継承されないが、実体はある

親の private フィールドも子のインスタンスの中にあるOK
public class Parent {
    private int secret = 42;
    public int getSecret() { return secret; }
}
public class Child extends Parent { }

new Child().getSecret();   // 42

new Child() で作られるインスタンスには、親の private フィールドの領域もちゃんと確保されています。子のコードから名前で直接触れないだけで、親の public や protected なメソッドを通せば間接的に読み書きできます。「継承されない＝存在しない」ではありません。

同じ名前のメソッドはオーバーライドにならない最頻出
public class Parent {
    private void priv() { System.out.println("Parent"); }
    public  void call() { priv(); }
}
public class Child extends Parent {
    public void priv() { System.out.println("Child"); }   // 別物の新メソッド
}

new Child().call();   // Parent

Child の priv() は親の priv() をオーバーライドしていません。private は継承されないので、たまたま同じ名前の別メソッドです。だから親の call() から呼ばれるのは親の priv() で、多態は起きません。子の方に @Override を付けるとコンパイルエラーになります。

2. 修飾子なしは、パッケージが違うと継承されない

別パッケージの子からは見えないNG
package app;
import lib.Parent;

public class Child extends Parent {
    void t() { pkg(); }         // コンパイルエラー: cannot find symbol
    @Override void pkg() { }    // コンパイルエラー: 何もオーバーライドしていない
}

@Override を外せば void pkg() { } は通りますが、それは private と同じく子が新しく作った別のメソッドです。

3. protected は「参照の型」で決まる

別パッケージの子の中から呼ぶ最重要
package app;
import lib.Parent;

public class Child extends Parent {
    void t() {
        prot();                    // OK
        this.prot();               // OK
        super.prot();              // OK

        Child other = new Child();
        other.prot();              // OK ← 別のインスタンスでも Child 型なら届く

        new Parent().prot();       // コンパイルエラー
        Parent p = this;
        p.prot();                  // コンパイルエラー ← this そのものでも Parent 型なら届かない
    }
}
// error: prot() has protected access in Parent

「自分のインスタンスなら OK、別のインスタンスは NG」と覚えると、上の2か所で外します。判定の基準はインスタンスではなく、参照の型です。自分のクラス（またはその子孫）の型の参照を通したときだけ届きます。other は別のインスタンスでも Child 型なので OK、p は this そのものなのに Parent 型なので NG です。

4. 子と同じパッケージでも、子クラスでなければ届かない

子と同じパッケージの、継承していないクラスから最頻出
package app;

public class Main {                     // Child と同じ app パッケージ。継承はしていない
    public static void main(String[] args) {
        Child c = new Child();
        c.pub();                        // OK
        c.prot();                       // コンパイルエラー
    }
}
// error: prot() has protected access in Parent

prot() は Child に継承されていますが、アクセスできるかどうかは、宣言した場所（lib.Parent）を基準に判定されます。Main は lib パッケージの住人でもなく、Parent の子でもないので、どちらの権限も持っていません。「Main と Child は同じパッケージだから呼べる」という選択肢は誤りで、答えはコンパイルエラーです。

逆に、親と同じパッケージからなら届く対比
package lib;

public class Helper {                   // Parent と同じ lib パッケージ
    void t() {
        new app.Child().prot();         // OK ← lib パッケージの権限で届く
    }
}

5. protected コンストラクタ

super() は呼べるが、new はできない要注意
// lib/Base.java
package lib;
public class Base { protected Base() { } }

// app/Sub.java
package app;
public class Sub extends lib.Base {
    Sub() { super(); }             // OK
    void t() { new lib.Base(); }   // コンパイルエラー
}
// error: Base() has protected access in Base

コンストラクタも同じ考え方です。別パッケージの子に許されるのは、自分を作る途中で親の部分を初期化する super() だけです。親を単独で new することはできません。

6. オーバーライドで広げるのは可、狭めるのは不可

親の修飾子子で書ける修飾子
publicpublic のみ
protectedprotected / public
なしなし / protected / public（同じパッケージの子のみ）
privateオーバーライドできない（継承されない）

狭めてはいけない理由は第5章 03 のとおりです。親の型で扱ったときに呼べるはずのメソッドが、子の実体では呼べなくなってしまいます。

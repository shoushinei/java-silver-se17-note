SE 16 で正式化。SE 17 試験の新規範囲で、毎回出ると考えてください。11 の教材には載っていません。

何のための構文か

「値を運ぶだけのクラス」を書くと、フィールド・コンストラクタ・ゲッター・equals・hashCode・toString で毎回50行ほどになります。record はそれを1行に畳むための構文です。

コンパイル結果を覗く ── ここに全部書いてある

規則を暗記する必要はありません。javap でコンパイル結果を見れば、試験に出る事実がそのまま並んでいます。

javap -p Point の出力最重要
public record Point(int x, int y) { }

// ↓ javac した後、javap -p Point で見えるもの

public final class Point extends java.lang.Record {
  private final int x;
  private final int y;
  public Point(int, int);
  public final java.lang.String toString();
  public final int hashCode();
  public final boolean equals(java.lang.Object);
  public int x();
  public int y();
}

この9行から、record の論点がほぼ全部導けます。

出力の行そこから分かること
public final class暗黙に final。継承できない（cannot inherit from final）
extends java.lang.Record親が既に埋まっている。単一継承なので extends を書けない
private final int x;p.x は不可。再代入も不可（setter が作れない）
public Point(int, int)標準コンストラクタ。record 本体と同じ public。狭められない
public int x();アクセサは getX() ではない。フィールドと同名で、括弧の有無だけが違う
equals / hashCode / toString3つとも自動生成。コンポーネントの一覧だけから作られる
インスタンスフィールドが x, y だけ追加できない。状態はコンポーネントがすべて

手書きに直すと

同じ意味のクラスを自分で書いた場合図
public final class Point extends java.lang.Record {

    private final int x;                       // ① private かつ final
    private final int y;

    public Point(int x, int y) {               // ② 標準コンストラクタ
        this.x = x;
        this.y = y;
    }

    public int x() { return this.x; }          // ③ アクセサ（同名・括弧あり）
    public int y() { return this.y; }

    public final boolean equals(Object o) {    // ④ コンポーネントを1つずつ比較
        if (this == o) return true;
        if (!(o instanceof Point p)) return false;
        return this.x == p.x && this.y == p.y;
    }

    public final int hashCode() {              // ⑤ コンポーネントから計算
        return Integer.hashCode(x) * 31 + Integer.hashCode(y);
    }

    public final String toString() {           // ⑥ クラス名[名前=値, ...]
        return "Point[x=" + x + ", y=" + y + "]";
    }
}

実際のバイトコードでは、equals / hashCode / toString は invokedynamic で java.lang.runtime.ObjectMethods を呼び、実行時に生成されます。
ただし意味は上の手書き版と同じなので、試験対策としてはこの形で理解して構いません。この仕組みのおかげで「コンポーネントの一覧」が唯一の情報源になり、3つのメソッドの整合性が構造的に保証されています。

javap の出力で final が付いているのは toString / hashCode / equals の3つだけで、アクセサ x() には付いていません。
ただしこの final は「サブクラスからのオーバーライド禁止」を意味するもので、record 自身の定義で上書きすることは4つとも可能です。自分で書けば、その分は生成されません。

5点セットとしての整理

この1行が展開されるまとめ
record Point(int x, int y) { }

// ↓ コンパイラが自動生成するもの（5点セット）
//
//   private final int x;
//   private final int y;                    ① フィールド（すべて final）
//   Point(int x, int y) { ... }             ② 標準コンストラクタ
//   public int x()   public int y()         ③ アクセサ（getX ではない）
//   public boolean equals(Object o)         ④ 中身で比較
//   public int hashCode()                   ⑤ 中身から計算
//   public String toString()                   Point[x=1, y=2] 形式

括弧の中の int x, int y をコンポーネントと呼びます。この名前がそのままフィールド名・コンストラクタ引数名・アクセサ名になります。

実行結果OK
Point p = new Point(1, 2);

System.out.println(p);                        // Point[x=1, y=2]
System.out.println(p.x());                    // 1
System.out.println(p.equals(new Point(1,2))); // true ← 中身が同じなら等しい

アクセサ名は getX() ではなくコンポーネント名と同じ x()です。JavaBeans の慣習に従っていません。
また p.x（括弧なし）はフィールドが private なのでエラー。この2つが最頻出の引っかけです。

コンストラクタは3種類

黒本の record 問題はほぼ全部コンストラクタです。名前と役割を正確に区別してください。

名前書き方フィールドへの代入
標準コンストラクタ何も書かない（自動生成）自動
正規コンストラクタ引数リストを書く全フィールド自分で
コンパクトコンストラクタ引数リストを書かない自動（最後に追加）

3つに共通するのは引数リストがコンポーネントと一致していることです。コンパクト形式は括弧を省略しているだけで、実際の引数は他の2つと同じ。
だから3つは同時に存在できません。1つの入口を3通りの方法で埋めているだけです。javap で見ると、どれも public Data(java.lang.String); という同一のものが生成されています。

正規とコンパクトを両方書くと重複NG
public record D(String v) {
    public D { }
    public D(String v) { this.v = v; }
}
// error: constructor D(String) is already defined in record D

① 標準コンストラクタ

何も書かない基本
record S1(String v, int n) { }

new S1("  abc  ", 5);      // S1[v=  abc  , n=5]  加工なし。渡した値がそのまま

全コンポーネントを受け取り、全フィールドに代入するだけのものが自動生成されます。アクセス修飾子はrecord 本体と同じ。加工も検証もしません。

② 正規コンストラクタ

引数リストを書き、全フィールドに代入する要注意
record S2(String v, int n) {
    S2(String v, int n) {          // 引数リストがコンポーネントと完全一致 ← 目印
        if (v == null) throw new IllegalArgumentException();
        v = v.trim();
        System.out.println("検証してから…");
        this.v = v;                // ← this. を書く。位置は自由（最後でもよい）
        this.n = n * 10;
    }
}
new S2("  abc  ", 5);      // S2[v=abc, n=50]
1つでも代入を忘れると止まるNG
S2(String v, int n) { this.v = v; }
// error: variable n might not have been initialized

要件は「全フィールドに漏れなく代入すること」だけで、書く位置は自由です。「最初に書かなければならない」という制約はありません。

③ コンパクトコンストラクタ

括弧が無い形最頻出
record S3(String v, int n) {
    S3 {                                   // 引数リストが無い ← 目印
        if (n < 0) throw new IllegalArgumentException("負の数");
        if (v == null) v = "(未設定)";      // 引数を差し替える
        v = v.trim();                       // 加工する
    }
}
new S3("  abc  ", 5);      // S3[v=abc, n=5]
new S3(null, 5);           // S3[v=(未設定), n=5]
実行の流れ図
new Data("x")
    ↓
① 引数 value に "x" が入る          ← フィールドはまだ空
    ↓
② コンパクトコンストラクタの本体が動く
      ここで value を検証・加工できる
    ↓
③ this.value = value;  が自動追加される
    ↓
④ 完成

②の時点でフィールドはまだ未代入です。final フィールドは「確実に代入済み」と判定できるまで参照できないので、書くことも読むこともできません。

書き方結果
value（引数変数）○ 読める・書ける
this.value = x;✗ cannot assign a value to final variable value
if (this.value == null)✗ variable value might not have been initialized

加工した引数の値がそのままフィールドに入ります。③の自動代入が最後に走るためです。

return は書けない／修飾子は狭められないNG
public record H(int x) { public H { if (x > 0) return; } }
// error: invalid compact constructor in record
//        （途中で抜けると自動代入が走らないため）

public record I(int x) { private I { } }
// error: invalid canonical constructor in record I
//        （record 本体より狭くできない）

用途は検証と正規化の2つだけです。record は不変オブジェクトなので、生成の瞬間が値を検査できる唯一のタイミング。ここを通さずにインスタンスを作る経路が無いよう設計されています。
実務では②でできることは③でもできるうえ、③のほうが短く代入漏れの心配もありません。コンパクト形式が第一選択です。

3種類の外側 ── オーバーロードされたコンストラクタ

引数リストがコンポーネントと一致しないものは、上の3種類のどれでもありません。普通のクラスと同じコンストラクタのオーバーロードです。

this(...) で3種類のどれかへ合流する最頻出
public record Data(String value) {
    public Data() {                 // 引数0個 ← コンポーネント(1個)と不一致
        this("sample");             // 第1文で標準コンストラクタを呼ぶ
    }
}
new Data();        // Data[value=sample]
2つの禁止事項NG
public Data() { this.value = "sample"; }
// error: constructor is not canonical, so its first statement
//        must invoke another constructor of class Data
//        （フィールドへの直接代入は不可）

public Data() { System.out.println("x"); this("a"); }
// 同じエラー（this(...) は「第1文」でなければならない）

普通のクラスなら、それぞれのコンストラクタが独立してフィールドに代入できます（節05の this() 参照）。record はそれを禁じ、初期化の出口を1つに絞っています。
どんな引数で作られても必ず標準／正規／コンパクトのどれかを通るので、そこに書いた検証をすり抜ける経路が存在しません。

2種類の this を混同しない

書き方意味制約
this.value（ドット）フィールドを指す正規では書く。コンパクトと外側では禁止
this(...)（括弧）別のコンストラクタを呼ぶ外側で第1文に必須

「最初に this」という制約があるのは括弧の方だけです。ドットの方（正規コンストラクタの代入）に位置の制約はありません。
ドットか括弧かで見分けてください。ここを混ぜると、空欄補充問題（this("sample") を選ぶ）とエラー判定問題（this.value で落ちる）の区別がつかなくなります。

判定フロー

括弧の有無を最初に見る最重要
コンストラクタが書かれているか？
  いいえ ─→ 標準コンストラクタ
  はい  ─→ 引数リストの括弧はあるか？
             ない ─→ コンパクト（代入は自動。this. は禁止）
             ある ─→ コンポーネントと一致するか？
                       一致  ─→ 正規（全フィールドに this. で代入）
                       不一致 ─→ オーバーロード（第1文で this(...) 必須）

出題パターン① 引数なしコンストラクタを足した

これ単体ではコンパイルエラー頻出
public record Data(String value) {
    public Data() {
    }
}
// error: constructor is not canonical, so its first statement
//        must invoke another constructor of class Data
修正の方針書き方
正規にするpublic Data(String value) { this.value = value; }
引数を1つ受け取る＋フィールドを初期化。両方必要
合流させるpublic Data() { this("sample"); }
引数だけ直しても足りない要注意
public Data(String value) {          // 正規になったが本体が空
}
// error: variable value might not have been initialized

「String 引数を1つ受け取るようにする」と「フィールド value を初期化する」はセットで初めて正解です。片方だけでは別のエラーに移るだけ。2つ選択の問題では、この2つが答えになります。

出題パターン② 空欄に入るコードを選ぶ

選択肢の判定頻出
public record Data(String value) {
    public Data() {
        // insert code here
    }
}
選択肢結果理由
this("sample");○ 正解引数1個の標準コンストラクタへ合流
this();×recursive constructor invocation 自分自身を呼んでいる
super();×record に super() は書けない
super("sample");×同上
this.value = value;×直接代入は禁止。そもそも value が存在しない

正誤の分かれ目はthis に引数を渡しているかだけです。"sample" という文字列自体に意味はなく、合流先が要求する String を埋めるための値。"" でも null でも動きます。
super 系は常に誤り。record は暗黙に java.lang.Record を継承していますが、書き手が super() を触る余地はありません。

出題パターン③ コンパクト形式で this.value を読む

this. が1つ付いているだけ最頻出
public record Data(String value) {
    public Data {
        if (this.value == null) {                    // ← this. を付けた
            System.out.println("value is null");
        }
    }
}
// error: variable value might not have been initialized
this. を外せば通るOK
public Data {
    if (value == null) { System.out.println("value is null"); }
}

new Data(null);                     // value is null
new Data(null).value();             // null（自動代入で null が入る）

出題パターン④ アクセサとインタフェースの衝突

戻り値型が食い違う頻出
public interface Test {
    default void value() { System.out.println("A"); }   // 戻り値 void
}

public record Data(String value) implements Test { }
// error: value() in Data cannot implement value() in Test
//   return type String is not compatible with void

record は public String value() というアクセサを自動生成します。インタフェースは void value() を要求している。名前と引数が同じで戻り値型だけが違うので、オーバーライドとして成立しません（節06の「戻り値型だけ違うのは区別されない」と同じ根拠）。

エラーが出るのは data.value() を呼んでいる行ではなく、record の宣言行です。クラス定義そのものが成立していないので、main を読む手前で終わります。
戻り値型を String に揃えれば通り、そのときは B が出力されます。アクセサが default メソッドに勝つためです（第5章「クラスの具象メソッドは default に勝つ」）。

判定手順は2段階です。
① インタフェースのメソッド名がコンポーネント名と同じか
② 同じなら、戻り値型がコンポーネントの型と一致するか
不一致ならコンパイルエラー、一致するならアクセサが勝って default は使われません。default void の void が最重要の1語になります。

自動生成を上書きできる

アクセサも toString も差し替え可能要注意
record R5(int x) {
    public int x() { return x * 1000; }        // アクセサを上書き
    public String toString() { return "カスタム"; }
}
new R5(3).x();        // 3000
アクセサの形は変えられないNG
record E2(int x) {
    void x() { }                               // 戻り値型が違う
}
// error: invalid accessor method in record E2

自分で書けば自動生成は行われません。ただしアクセサは「引数なし・コンポーネントと同じ型を返す public メソッド」という形を守る必要があります。equals や hashCode も同様に上書きできます。

できること・できないこと

可否エラーメッセージ
static フィールド・メソッド○—
インスタンスメソッド○—
インタフェースの実装○—
ネスト・ローカル・ジェネリック○—
コンポーネントの可変長引数○—
インスタンスフィールドの追加×field declaration must be static
他クラスの継承（extends）×暗黙に Record を継承済み
record を継承する×cannot inherit from final
abstract にする×modifier abstract not allowed here
フィールドの再代入（setter）×すべて final
標準／正規コンストラクタを狭める×attempting to assign stronger access privileges
禁止はインスタンスフィールドの追加だけ頻出
record W(int x) {
    static final int MAX = 100;                // static は OK
    static W of(int v) { return new W(v); }    // static メソッドも OK
    int doubled() { return x * 2; }            // インスタンスメソッドも OK
}
インタフェースは実装できるOK
interface Named { String label(); }

record Person(String name) implements Named {
    public String label() { return "名前:" + name; }
}
Named n = new Person("A");     // 多態も普通に使える

禁止されているのはインスタンスフィールドの追加と継承だけです。「record にはメソッドを書けない」「record はインタフェースを実装できない」はどちらも誤りで、選択肢に出ます。
暗黙に final かつ暗黙に java.lang.Record のサブクラスなので、継承の口が上下とも塞がっていると覚えると整理できます。

細かいが出る論点

コンポーネントゼロも可変長も書ける要注意
record Empty() { }                 // Empty[]
record V(int... nums) { }          // 可変長引数もコンポーネントにできる
record Box<T>(T value) { }         // ジェネリックも可
ネストとローカル要注意
public class G {
    record Nest(int a) { }                     // ネストした record は暗黙に static
    public static void main(String[] x) {
        record Local(String s) { }             // メソッド内にも定義できる
        System.out.println(new Local("ok"));   // Local[s=ok]
    }
}
配列コンポーネントの equals最重要
record A(int[] arr) { }

new A(new int[]{1,2}).equals(new A(new int[]{1,2}));   // false !

// 自動生成される equals は各コンポーネントを
//   基本データ型 → ==
//   参照型       → その型の equals
// で比較する。配列の equals は「同じ実体か」なので false になる

「record は中身で比較する」はコンポーネントが配列のときだけ成り立ちません。配列の equals は Object のもの（参照比較）だからです。
toString も A[arr=[I@44a664f2] のようになります。第2章の「配列に equals は効かない」がそのまま持ち込まれる形です。

第5章とつながります。record は暗黙に final なので sealed インタフェースの実装先としてそのまま使えます（final / sealed / non-sealed の宣言が不要）。

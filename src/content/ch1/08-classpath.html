パッケージ付きのコンパイルと実行 ── -d と -cp

1ファイルだけなら javac Main.java と java Main で済みます。パッケージに属するクラスが複数になると、「.class をどこに書き出すか」と「JVM にどこを探させるか」を指定する必要が出てきます。前者を決めるのが javac -d、後者を決めるのが java -cp です。

この節の例は、次のファイル構成で、app ディレクトリの1つ上でコマンドを打つ前提です。

この節で使うファイル構成前提
作業ディレクトリ（ここでコマンドを打つ）
└── app/
    ├── Item.java     // package app;  public class Item { ... }
    └── Main.java     // package app;  public class Main { main の中で Item を使う }

大前提 ── JVM はクラスをどう探すか

探すファイルの決まり方最重要
探すファイル ＝ クラスパス / パッケージ名の . を / にしたもの / クラス名.class

java -cp build app.Main    →  build/app/Main.class を探す
java app.Main              →  ./app/Main.class を探す（-cp が無ければカレントディレクトリ）

java に渡すのはファイルのパスではなく、クラスの完全修飾名（app.Main）です。JVM はこれを app/Main.class というパスに読み替え、クラスパスに書かれた場所を起点にしてそのファイルを探します。クラスパスとは「クラスを探し始める場所」の一覧のことで、-cp で指定します。

パッケージ名とディレクトリの階層は一致していなければなりません（第1章 05）。だから -cp に書くのはパッケージの一番上のディレクトリ（app）が入っている場所で、パッケージのディレクトリそのもの（build/app）ではありません。

javac -d ── .class の書き出し先

-d を付けない場合図
$ javac app/Item.java app/Main.java

app/
├── Item.java
├── Item.class      ← .java と同じ場所にできる
├── Main.java
└── Main.class
-d build を付けた場合図
$ javac -d build app/Item.java app/Main.java

app/
├── Item.java
└── Main.java
build/              ← 無ければ作られる
└── app/            ← パッケージ名のディレクトリも自動で作られる
    ├── Item.class
    └── Main.class

-d の後ろは書き出し先の一番上のディレクトリです。その下にパッケージの階層（app/）を javac が自動で作り、.class を置きます。-d を付けなければ、.class は元の .java と同じディレクトリにできます。-d の d は directory（出力先ディレクトリ）です。

java -cp ── クラスを探す場所

書き方意味
java -cp build app.Mainbuild を起点に探す
-classpath build / --class-path build-cp と同じ。長い書き方
指定しないカレントディレクトリ（.）だけを探す（環境変数 CLASSPATH が無い場合）
-cp build:lib（Windows は build;lib）複数の場所を前から順に探す

-cp の cp は class path です。javac にも同じ -cp があり、こちらはコンパイル時に参照する、コンパイル済みの .class の場所を指定します。

組み合わせを判定する

コンパイル実行結果理由
javac -d build app/Item.java app/Main.javajava -cp build app.Main○build/app/Main.class が見つかる
javac app/Item.java app/Main.javajava app.Main○-d なしなので ./app/Main.class にあり、-cp なしのカレントから見つかる
javac app/Item.java app/Main.javajava -cp build app.Main×.class は app/ にあり、build は存在しない
javac -d build app/Item.java app/Main.javajava app.Main×./app/Main.class を探すが、実物は build/app/ にある
javac -d build app/Item.java app/Main.javajava build.app.Main×ファイルは見つかるが、中身のクラス名は app.Main。名前が違う
javac -d build app/Item.java app/Main.javajava -cp build/app Main×同じく名前が違う。起点をパッケージの中にしてはいけない
エラーは2種類ある実行時
$ java -cp build app.Main          // ○
item

$ java app.Main                     // ファイルが見つからない
Error: Could not find or load main class app.Main
Caused by: java.lang.ClassNotFoundException: app.Main

$ java build.app.Main               // ファイルは見つかるが、名前が違う
Error: Could not find or load main class build.app.Main
Caused by: java.lang.NoClassDefFoundError: build/app/Main (wrong name: app/Main)

ClassNotFoundException はファイルが見つからない、NoClassDefFoundError ... (wrong name) は見つかったファイルの中身が、指定した名前のクラスではないという意味です。
java build.app.Main と書くと、JVM は ./build/app/Main.class を見つけます。しかしその中のクラスは package app; で宣言された app.Main なので、名前が合いません。パッケージ名はソースの package 宣言で決まるもので、置いた場所によって変わるものではありません。

判定の手順

  1. javac に -d があるかを見る。あれば .class は「-d の後ろ／パッケージの階層」の中、なければ .java の隣にできる
  2. java の -cp を見る。無ければカレントディレクトリが起点
  3. 「起点 / パッケージ名の . を / にしたもの / クラス名.class」に、1. でできたファイルがあるかを確かめる
  4. java に渡した名前が、package 宣言どおりの完全修飾名になっているかを確かめる

選択肢が4つ並んでいても、見るのは「どこにできたか」と「どこを探しているか」が一致しているかだけです。一致していて、名前も完全修飾名なら ○ です。

細かいけれど問われる点

項目内容
渡すものの違いjavac にはファイルのパス（app/Main.java）、java にはクラス名（app.Main）
拡張子java -cp build app.Main.class は ×。ClassNotFoundException: app.Main.class
スラッシュ区切りjava -cp build app/Main は、実際の JDK では起動ランチャーが / を . に読み替えて動きます。ただし正式な指定はドット区切りの完全修飾名なので、選択肢に両方あればドット区切りを選ぶ
1ファイルだけ渡した場合javac -d build app/Main.java だけでも、Main が使っている app/Item.java を javac が探し出して一緒にコンパイルし、build/app/Item.class もできる
ソース実行モードSE 17 では渡した1ファイルしかコンパイルしないので、別ファイルの Item を使う java app/Main.java は動かない（Java 22 以降は複数ファイルも扱える）

コマンドの基本（なぜ javac はファイル名で java はクラス名なのか）は第1章 03、パッケージとディレクトリの対応は第1章 05にあります。

09

try-with-resources

リソースを自動的に閉じる構文です（Java 7〜）。SE 11 Silver の範囲外だったため、ここは完全な新規範囲です。

基本形形
try (BufferedReader br = new BufferedReader(new FileReader("a.txt"))) {
    // 処理
} catch (IOException e) {
}
// finally に close() を書かなくても自動で閉じられる

ルール

  • リソースは AutoCloseable を実装したクラスでなければならない
  • 複数書くときは ; 区切り
  • 閉じられる順序は宣言と逆順（後ろから閉じる）
  • リソース変数は暗黙的に final。中で再代入するとコンパイルエラー
  • catch も finally も省略可能（通常の try と違い、try 単体で成立する）
閉じる順は b → a要注意
try (A a = new A(); B b = new B()) {
    // 宣言は a → b、close は b → a
}

実行順序の罠

close() は catch や finally より先に実行されます。

try → close → catch → finally最重要
try (Res r = new Res()) {
    System.out.println("try");
    throw new Exception();
} catch (Exception e) {
    System.out.println("catch");
} finally {
    System.out.println("finally");
}
// 出力: try → (close の中身) → catch → finally

「close と catch のどちらが先か」は定番の出題です。リソースの後始末が終わってから例外処理に入る、と覚えてください。

Java 9 からの拡張

宣言済みの final 変数を書けるOK
Res r = new Res();
try (r) {           // Java 9 以降は OK
}

AutoCloseable の正体

try(...) の括弧に書けるのは、AutoCloseable を実装した型だけです。このインタフェースの中身はこれだけです。

抽象メソッド1つだけのインタフェース最重要
public interface AutoCloseable {
    void close() throws Exception;        // これ1つだけ
}

// java.io.Closeable は AutoCloseable のサブインタフェース
public interface Closeable extends AutoCloseable {
    void close() throws IOException;      // 例外を IOException に狭めている
}

Closeable が例外を IOException に絞れているのは、第5章 節03の「オーバーライドで検査例外は狭められる」規則によります。IOException は Exception のサブクラスなので合法です。

括弧の中は何をしているか

try (Res r = new Res()) の括弧の中は、ただの変数宣言です。close() はここには書かれていません。

コンパイラが生成するコード図
// 書いたコード
try (Res r = new Res()) {
    処理;
}

// コンパイラが生成するもの（イメージ）
Res r = new Res();                    // ① 括弧の中＝リソースを開く
try {
    処理;                              // ② 本体
} finally {
    if (r != null) r.close();         // ③ 自動で足される
}

つまり try(...) の括弧は「この変数を宣言して、ブロックを抜けるときに close() を呼んでおいて」という指示です。
自分のコードに close() は一度も登場しません。呼び出しを書き忘れないよう、コンパイラに生成させるための構文です。

close() の中身は自分で書く

Java は「何を閉じるか」を知らないので、close() に決まった処理はありません。コンストラクタで開いたものを閉じるのが典型です。

開く処理と対になるものを書くOK
class Res implements AutoCloseable {
    private FileWriter w;

    Res() throws IOException {
        w = new FileWriter("out.txt");    // 開く
    }

    @Override
    public void close() throws IOException {
        w.close();                         // 閉じる
    }
}
標準クラスclose() がやること
FileWriterバッファの内容をファイルに書き出し、ファイルハンドルを OS に返す
FileInputStreamファイルハンドルを OS に返す
Connection（JDBC）DB との接続を切る／プールに返却する
Socket通信を終了しポートを解放する
Scanner内部の入力ストリームを閉じる

なぜ返す必要があるのか。ガベージコレクションが回収するのはJava のメモリだけだからです。
ファイルを開くと OS 側にも記録（ファイルディスクリプタ）が作られます。Java 側のオブジェクトが GC で消えても、OS 側の記録は残ったまま。これが溜まると上限に達し、新しくファイルを開けなくなります。
FileWriter にはもう1つ役割があり、close() しないとバッファの内容がファイルに書かれません。

実装しないと2通りのエラーになる

implements を書き忘れたNG
class Res { public void close(){} }        // close() はあるが implements が無い

try (Res r = new Res()) { }
// error: try-with-resources not applicable to variable type
//        (Res cannot be converted to AutoCloseable)
close() を書き忘れたNG
class Res implements AutoCloseable { }
// error: Res is not abstract and does not override
//        abstract method close() in AutoCloseable

コンパイラは「close() という名前のメソッドがあるか」ではなく、AutoCloseable 型として扱えるかで判断します。第5章の「宣言型が呼べる範囲を決める」と同じ理屈です。
try(...) を見たら、そのクラスが AutoCloseable を実装しているか最初に確認してください。実装が無い選択肢で「コンパイルエラー」を選ばせる問題が出ます。

Java 9 の形には条件がある

再代入された変数は書けない要注意
Res r = new Res();
r = new Res();          // 再代入した
try (r) { }
// error: variable r used as a try-with-resources resource
//        neither final nor effectively final

閉じる対象が途中ですり替わると、どれを閉じるべきか決まりません。そのため final または実質 final（一度も再代入していない）である必要があります。

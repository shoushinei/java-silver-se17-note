Iterable / Collection / List / Path の関係

問題文では、変数の型として ArrayList や List だけでなく、Collection や Iterable、Path も使われます。これらはどれもインタフェースで、親子関係でつながっています。上にある型ほど約束していることが少なく、呼べるメソッドも少ない、というのが全体を貫く見方です。

全体図

親子関係（上が親）最重要
Iterable<T>                 「1つずつ取り出せる」＝拡張for文で回せる、とだけ約束する
 ├── Collection<E>          要素の集まり。add / remove / size / contains
 │    ├── List<E>           順番と位置（インデックス）がある。重複してよい
 │    │    └── ArrayList<E>  ← 実際に new するのはこのクラス
 │    ├── Set<E>            重複しない
 │    │    └── HashSet<E>
 │    └── Queue<E>          先頭から順に取り出す
 └── Path                    ファイルやディレクトリの「場所」（Iterable<Path> を継承）

Map<K, V>                   キーと値の組。Collection でも Iterable でもない（別系統）
 └── HashMap<K, V>

ArrayList と HashSet と HashMap 以外は、すべてインタフェースです。インタフェースは new できないので、実物を作るときは new ArrayList<>() や List.of(...)、Path.of(...) を使います。

それぞれの正体

型種類 / パッケージ何を表すか主なメソッド
Iterable<T>インタフェース
java.lang（import 不要）		1つずつ取り出せるものiterator() forEach(...)
Collection<E>インタフェース
java.util		要素の集まりadd remove contains size isEmpty clear
List<E>インタフェース
java.util		順番のある集まり上に加えて get(int) set(int, E) add(int, E) indexOf
ArrayList<E>クラス
java.util		List の代表的な実装List のすべて
Pathインタフェース
java.nio.file		ファイルの場所（パス）getFileName() getParent() getNameCount()

Iterable は java.lang パッケージなので import なしで使えます。Collection と List は java.util、Path は java.nio.file なので import が必要です。import が無いと cannot find symbol のコンパイルエラーになります（第1章 06）。

親の型の変数に入れられる。呼べるメソッドは変数の型で決まる

同じ ArrayList でも、変数の型で呼べるものが変わる最頻出
List<String> list = new ArrayList<>(List.of("a", "b"));
Collection<String> col = list;          // OK（子 → 親）
Iterable<String>   it  = list;          // OK

col.add("c");                            // OK  Collection にある
col.size();                              // OK
col.get(0);                              // コンパイルエラー: get は List にしかない
it.size();                               // コンパイルエラー: Iterable には size も無い

List<String> l2 = col;                   // コンパイルエラー: 親 → 子はキャストが必要
List<String> l3 = (List<String>) col;    // OK（実体が ArrayList なので）

変数 col が指しているのは ArrayList で、実物は get を持っています。それでも col.get(0) がエラーになるのは、コンパイラは変数の型（Collection）しか見ないからです。第5章 05「宣言型か実体型か」と同じ規則で、クラスの継承だけでなくインタフェースでも同じように働きます。

インタフェースは new できないNG
List<String> a = new List<>();          // コンパイルエラー: List is abstract; cannot be instantiated
Collection<String> b = new Collection<>();   // コンパイルエラー
Path c = new Path("a.txt");              // コンパイルエラー

List<String> d = new ArrayList<>();     // OK
Path e = Path.of("a.txt");               // OK

型引数に親子関係は無い ── List<Animal> と List<Dog>

class Dog extends Animal のとき、要素として入れるのと、リストごと代入するのとで結果が変わります。

親の型のリストに、子を入れるのは OKOK
List<Animal> animals = new ArrayList<>();
animals.add(new Dog());          // OK。Dog は Animal の一種
animals.add(new Animal());       // OK
Animal first = animals.get(0);   // 取り出すと Animal 型
子の型のリストに親は入れられない。リスト同士の代入も不可頻出
List<Dog> dogs = new ArrayList<>();
dogs.add(new Animal());                      // コンパイルエラー: Animal cannot be converted to Dog

List<Animal> a1 = new ArrayList<Dog>();      // コンパイルエラー
List<Animal> a2 = dogs;                      // コンパイルエラー: List<Dog> cannot be converted to List<Animal>

Collection<Dog> c = new ArrayList<Dog>();    // OK ← 変わるのが < > の外側だけならよい

Dog が Animal の子でも、List<Dog> は List<Animal> の子ではありません。もし代入できると、a2.add(new Animal()) で Dog 専用のリストに Animal が紛れ込んでしまうからです。
親子関係を使えるのは < > の外側（ArrayList → List → Collection）だけで、< > の中身は左右で完全に一致させます（右辺を <> にすれば自動で一致します）。

配列は逆に Animal[] arr = new Dog[1]; がコンパイルできてしまい、Animal を入れたときに実行時の ArrayStoreException で止まります（第2章 11 配列）。ジェネリクスは同じ事故をコンパイルの時点で防ぐ設計です。

拡張for文で回せるのは「配列」か「Iterable」だけ

型拡張for文理由
配列○言語が特別に扱う
Iterable / Collection / List / Set○どれも Iterable（またはその子）
Path○Iterable<Path> を継承している。パスの各部分を1つずつ取り出す
Map×Iterable ではない。keySet() / values() / entrySet() を回す
String×Iterable ではない。toCharArray() で char[] にすれば回せる
Map と String は直接回せない頻出
Map<String, Integer> map = new HashMap<>();
for (String k : map) { }              // コンパイルエラー: for-each not applicable to expression type
for (char c : "abc") { }              // コンパイルエラー: 同じ

for (String k : map.keySet()) { }     // OK  キーの Set
for (Integer v : map.values()) { }    // OK  値の Collection
for (char c : "abc".toCharArray()) { }   // OK  char[]
Path も拡張for文で回せる要注意
Path path = Path.of("dir", "sub", "file.txt");
for (Path p : path) {
    System.out.print(p + " ");        // dir sub file.txt
}

Path は「ファイルの場所」なので、回せると思わない人が多い型です。Path は Iterable<Path> を継承しているので、拡張for文に使えます。取り出されるのはファイルの中身ではなく、パスを区切った各部分（dir、sub、file.txt）です。反対に、名前から回せそうに見える Map と String は回せません。

Path ── ファイルの「場所」を表す型

作り方と主なメソッドOK
import java.nio.file.Path;
import java.nio.file.Paths;

Path p1 = Path.of("dir", "sub", "file.txt");   // Java 11 以降
Path p2 = Paths.get("dir/sub/file.txt");       // 古くからある書き方。結果は同じ

p1.getFileName();     // file.txt
p1.getParent();       // dir/sub
p1.getNameCount();    // 3

Path.of("no/such/file.txt");   // 例外にならない ← 場所を表すだけで、ファイルを確かめない

Path は場所を表すだけで、ファイルが本当にあるかは確かめません。存在しないパスを作っても例外になりません。実際にファイルを読み書きするのは Files クラスの static メソッドです。区切り文字の表示は OS によって違い、Windows では dir\sub と表示されます。

Files のメソッドは検査例外を投げる第6章とつながる
import java.nio.file.*;

void read() {
    Files.readAllLines(Path.of("a.txt"));
    // コンパイルエラー: unreported exception IOException;
    //                   must be caught or declared to be thrown
}

void read2() throws IOException {          // throws で宣言すれば OK（import java.io.IOException も必要）
    Files.readAllLines(Path.of("a.txt"));  // ファイルが無ければ実行時に NoSuchFileException
}

Files のメソッドはファイル操作に失敗する可能性があるので、検査例外の IOException を投げると宣言されています。だから catch するか throws で宣言しないとコンパイルエラーです。無いファイルを読んだときの NoSuchFileException は IOException の子です。検査例外とは何かは第6章 01、throws の書き方は第6章 07、try-with-resources は第6章 09にあります。

名前が似ているもの

名前正体
Collectionインタフェース。要素の集まり
Collectionsクラス。Collections.sort(list) のような static メソッドを集めた道具箱
Pathインタフェース。ファイルの場所
Pathsクラス。Paths.get(...) で Path を作る
Filesクラス。ファイル操作の static メソッドを集めた道具箱
Arraysクラス。配列用の static メソッドを集めた道具箱（Arrays.toString など）

末尾に s が付くものは、static メソッドを集めたクラスという共通点があります。Collection と Collections、Path と Paths を取り違えた選択肢に注意してください。

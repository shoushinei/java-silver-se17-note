09

インタフェース

省略された修飾子を補って読むのが、この節のすべてです。

暗黙に付くもの最重要
interface I {
    int X = 1;                    // 実際は public static final int X = 1;
    void m();                     // 実際は public abstract void m();
    default void d(){ }           // 実際は public default void d(){ }
    static void s(){ }            // 実際は public static void s(){ }
    private void h(){ }           // SE 9以降。private はそのまま
}
メンバ暗黙に付く修飾子
フィールドpublic static final（定数。再代入不可）
メソッド（本体なし）public abstract
default / static メソッドpublic
実装側で public を書き忘れる最頻出
interface I { void m(); }          // 暗黙に public

class C implements I {
    void m(){ }                     // 修飾子なし → public より狭い
}
// error: m() in C cannot implement m() in I
//        attempting to assign weaker access privileges; was public

インタフェースのメソッドは暗黙に publicなので、実装側も必ず public を書きます。節03の「アクセスを狭められない」がここに効いています。
これは非常によく出る引っかけです。

定数への再代入NG
interface I { int X = 1; }
I.X = 2;      // error: cannot assign a value to static final variable X
できることできないこと
複数のインタフェースを実装コンストラクタを持つ
インタフェース同士の多重継承インスタンスフィールドを持つ
extends と implements の併用インスタンス化する
順序は extends が先要注意
class C extends P implements A, B { }     // OK
class C implements A, B extends P { }     // コンパイルエラー

インタフェースもインスタンス化できない

抽象クラスと同じエラー頻出
interface I { void m(); }

new I();                    // error: I is abstract; cannot be instantiated
I i = new Impl();           // OK。型として使うのは自由

エラーメッセージは抽象クラスのときと一字一句同じです。インタフェースのメソッドは暗黙に abstract なので、本体を持たないものが含まれている ── 実体を作っても実行するコードが無いからです。
new できない2つ（抽象クラス・インタフェース）は、どちらも「未完成のメソッドを含んでいるから」という同じ理由です。

new できるか型として使えるか
普通のクラス○○
抽象クラス×○
インタフェース×○

new I(){ ... } のように後ろに { } が続く形（匿名クラス）は通りますが、これはインタフェースを実装した名前の無いクラスをその場で定義しているだけで、インタフェースのインスタンス化ではありません。匿名クラスは SE 17 の出題範囲外です。

同じメソッドを2つのインタフェースから受け継ぐとき

同じ名前・同じ引数の抽象メソッドを、2つのインタフェースから受け継ぐことがあります。1つのメソッドで両方の約束を満たせるかで決まります。

2つの宣言の戻り値型結果実装クラスが書く戻り値型
同じ（void run() と void run()）○それと同じ。1つ書けば両方を実装したことになる
片方が他方の子（List と Collection）○子のほう（List）か、さらにその子
互いに親子関係が無い（List と Set、int と long）×どう書いても両方は満たせない
List と Collection なら両立するOK
interface A { List<String> items(); }
interface B { Collection<String> items(); }

class C implements A, B {
    public List<String> items() { return List.of("x"); }   // OK。List は Collection の子
}
// public Collection<String> items() と書くと、A の約束（List を返す）を満たせずエラー
List と Set は両立しない頻出
interface A { List<String> items(); }
interface B { Set<String> items(); }

interface AB extends A, B { }      // コンパイルエラー: types B and A are incompatible
class C implements A, B { ... }    // 同じくコンパイルエラー

List でもあり Set でもあるものを返すメソッドは書けないので、受け継いだ時点でエラーになります。実装クラスだけでなく、extends A, B と書いたインタフェース自身がエラーになるのがポイントです。
戻り値の親子関係は節03 共変戻り値、List・Set・Collection の関係は第2章 14で確認できます。基本データ型には親子関係が無いので、int と long も両立しません。

片方が default でもう片方が抽象メソッドの場合（interface A { void run(); } と interface B { default void run(){ } }）、class C implements A, B { } はコンパイルエラーです。クラスでオーバーライドすれば解決します。2つとも default の場合は節10「default が衝突したら」を参照。

default / static / private メソッド

インタフェースが実装を持てるようになった経緯を知ると、規則が導けます。

Java 8 でラムダ式が入ったとき、List や Collection に forEach を追加したくなりました。しかし従来のインタフェースにメソッドを足すと世界中の実装クラスが一斉にコンパイルエラーになります。
そこで「実装を持ったメソッド」を許し、既存クラスを壊さずに機能追加できるようにした。default の本質は後方互換のための仕組みです。

defaultstaticprivate
実装クラスに継承される○××
呼び方インスタンス経由インタフェース名経由内部からのみ
オーバーライド○××
導入SE 8SE 8SE 9
static は実装クラスに継承されない頻出
interface G { static void s(){} default void d(){} }
class I implements G { }

new I().d();      // OK
I.s();            // error: cannot find symbol
G.s();            // OK。インタフェース名で呼ぶ

default が衝突したら

同じ名前の default を2つ実装最頻出
interface A { default void m(){ System.out.println("A"); } }
interface B { default void m(){ System.out.println("B"); } }
class C implements A, B { }
// error: types A and B are incompatible
解決はオーバーライド＋名指しOK
class C implements A, B {
    public void m(){
        A.super.m();       // インタフェース名.super.メソッド()
        B.super.m();
    }
}

Java は多重継承の曖昧さをコンパイラに解決させず、書き手に選ばせます。A.super.m() という構文は、この場面でしか使いません。

クラスが常に勝つ

エラーにはならない要注意
class Par { public void m(){ System.out.println("クラスが勝つ"); } }
interface In { default void m(){ System.out.println("インタフェース"); } }
class Sub extends Par implements In { }

new Sub().m();      // クラスが勝つ

クラスの具象メソッドと default が競合した場合、クラス側が無条件で優先されます。「クラスは実装、インタフェースは規約」という優先順位です。
第4章 節10の record のアクセサが default に勝つのも、この規則です。

Object のメソッドは default にできないNG
interface I { default String toString(){ return "x"; } }
// error: default method toString in interface I overrides a member of java.lang.Object

toString / equals / hashCode はすべてのクラスが Object から継承しており、「クラスが勝つ」規則によりその default が絶対に使われないため、書くこと自体が禁止されています。

default に付けられない修飾子エラー
finalmodifier final not allowed here
static / abstract / privateillegal combination of modifiers
protected / synchronized不可

private メソッド（SE 9以降）は、複数の default メソッドで共通処理をくくり出すために追加されました。private static も書けます。外部からは一切見えません。

サブインタフェースの default で、親の抽象メソッドを実装する

インタフェースがインタフェースの穴を埋める頻出
interface Shape {
    double area();                               // 抽象メソッド
}
interface Square extends Shape {
    double side();
    default double area() { return side() * side(); }   // 親の area() を default で実装
}
class Tile implements Square {
    public double side() { return 2; }           // area() は書かなくてよい
}

Shape s = new Tile();
System.out.println(s.area());    // 4.0

インタフェースは、extends した親インタフェースの抽象メソッドを default メソッドとして書き直せば「実装済み」にできます。Tile に残っている義務は、まだ本体の無い side() だけです。
Tile の中に area() が見当たらなくても、コンパイルエラーにはなりません。「どこかで本体が書かれているか」を、親インタフェースまでたどって確かめます。

逆向き ── default を抽象メソッドに戻す要注意
interface Greeter { default void hi() { System.out.println("hi"); } }
interface Silent extends Greeter { void hi(); }   // 本体無しで宣言し直す → 再び抽象

class Mute implements Silent { }
// error: Mute is not abstract and does not override abstract method hi() in Silent

サブインタフェースで本体無しで宣言し直すと、親の default は引き継がれず、抽象メソッドに戻ります。実装クラスは hi() を書かなければなりません。
判定の基準は、実装クラスから見て一番近い宣言に本体があるかどうかです。

メソッドに本体を書けるかは、修飾子で決まる

インタフェースのメソッドは4種類しかありません。修飾子を見れば、本体が要るか要らないかが一意に決まります。

書き方本体正体
void m();禁止暗黙に public abstract
default void m(){ }必要実装クラスに継承される
static void m(){ }必要インタフェース名で呼ぶ
private void m(){ }必要内部専用（SE 9+）
修飾子なしに本体を書くと最頻出
public interface S { void m(){ } }
// error: interface abstract methods cannot have body

public interface S { public void m(){ } }      // 同じエラー
public interface S { abstract void m(){ } }    // 同じエラー

エラーメッセージが答えを言っています。修飾子なし＝ abstract メソッドなので本体を持てません。public を明示しても abstract は消えないので同じです。
default は本体を書く許可証だと考えてください。SE 8 で導入したとき「本体を書いたら自動的にデフォルト実装になる」仕様にすると意図せず実装を提供してしまう危険があったため、明示的な宣言を要求する形にしました。

冗長な修飾子はエラーにならない

4通りとも同じ意味要注意
void m();                     // 標準的な書き方
public void m();              // public は冗長
abstract void m();            // abstract も冗長
public abstract void m();     // 両方冗長

暗黙に付くものを明示しただけなので、すべて正しい書き方です。選択肢に4つ並んでいて全部正解というパターンがあり得ます。

修飾子の可否 ── 一覧

修飾子付けられるか本体

インタフェースのメソッドに付けられるアクセス修飾子は public か private の2つだけ。protected と final は全滅。何も書かなければ public が補われます。この1行で、上の表の可否はすべて説明できます。

protected が使えないのは、インタフェースが「誰でも使える約束事」だからです。public か（内部専用の）private の2択しかなく、「サブクラスまで」という中間段階が成立しません。
final が使えないのは、インタフェースのメソッドがオーバーライドされるためにあるからです。default に付けようとしても同じ理由で弾かれます。

private メソッドの2つの罠

本体を省略できない頻出
public interface S { private void a(); }
// error: missing method body, or declare abstract

本体を省略すると暗黙に abstract が付く＝「実装クラスに書かせる」という意味になります。しかし private は実装クラスからも見えない。書いてほしい相手が、そのメソッドの存在を知らないという矛盾です。
private abstract も禁止なので、本体を書く以外に道がありません。

default と併用できない頻出
public interface S { private default void c(){ } }
// error: illegal combination of modifiers: private and default

private の用途 ── ただし文法上は独立

default の共通処理をくくり出すOK
interface S {
    private void log(String s){ System.out.println("[log] " + s); }   // 共通処理
    default void d1(){ log("d1"); }
    default void d2(){ log("d2"); }
}
// [log] d1
// [log] d2

SE 9 で追加された目的は、default が増えたときの重複を1か所にまとめることです。しかも内部の都合なので実装クラスには見せたくない。この2つの要求から生まれました。
ただし文法上は default の存在に依存しません。default が1つも無くても、呼び出し元が無くてもコンパイルは通ります。用途としてはセット、文法としては独立と分けて覚えてください。

「誰からも呼ばれないメソッドは意味がないのでは」と感じても、コンパイラは文法しか見ません。未使用の変数やメソッドはエラーになりません。
問題文が「記述してコンパイルできるコードを選べ」なら文法だけ、「実行結果を選べ」なら挙動、と何が問われているかを先に読むのがこの試験では一貫して効きます。

private の呼び出し元 ── static かどうかで変わる

private は「インタフェース内部の共通処理用」という理解で正しいです。ただし、インスタンスの private と private static で、呼べる相手が違います。

呼び出し元 ＼ 呼び出し先privateprivate static
default メソッド○○
private メソッド○○
static メソッド×○
実装クラス・外部××
static から private（インスタンス）は呼べない要注意
interface J {
    private void a() { }
    static void s() { a(); }   // コンパイルエラー
}
// error: non-static method a() cannot be referenced from a static context

理由はクラスの static と同じです。static メソッドにはインスタンス（this）が無いので、インスタンスに属する private メソッドは呼べません。default の共通処理なら private、static の共通処理なら private static と使い分けます。

super. と インタフェース名.super. の使い分け

書き方見に行く先
super.m()スーパークラスのみ。インタフェースは一切見ない
I.super.m()直接実装／継承したインタフェースの default メソッド
素の super はインタフェースを見ない最頻出
interface A { default void sample(){ System.out.println("Hello"); } }
interface B extends A { }

class C implements B {
    public void sample(){
        super.sample();          // error: cannot find symbol
    }
}
// C は extends を書いていない → スーパークラスは Object
// Object に sample() は無い

クラスの親は1つしかないので super だけで一意に決まります。インタフェースは複数実装できるので、どれのことか名指しが必要。だから前に名前が付きます。
覚え方は、super. は縦のライン（継承）を1段上る、名前.super. は横のライン（インタフェース）から名指しで取ってくる。

名指しできるのは「直接の親」だけ

間接的な祖先は指せない最頻出
interface A { default void sample(){ System.out.println("Hello"); } }
interface B extends A { }
class C implements B {
    public void sample(){
        A.super.sample();        // error: not an enclosing class: A
        B.super.sample();        // OK ── B は A から sample() を継承している
    }
}

C implements B なので、C から見た直接の親は B だけ。A は B の親であって C の直接の親ではありません。
判定は簡単で、implements（インタフェース内なら extends）の右に書かれている名前かどうかを見ます。A.super と B.super の1文字違いで正誤が変わります。

インタフェースの中でも使えるOK
interface A { default void m(){ System.out.println("A の default"); } }
interface B extends A {
    default void m(){ A.super.m(); System.out.println("B の default"); }
}
// 出力: A の default / B の default

// ただし素の super.m() はインタフェース内でも不可（スーパークラスが存在しない）
親クラス経由なら super. で届く要注意
interface I { default void m(){ System.out.println("I の default"); } }
class Base implements I { }              // m() を継承しているだけ
class Sub extends Base {
    void call(){ super.m(); }            // OK → I の default
}

super. は「インタフェースを見に行かない」のではなく、スーパークラスだけを見て、そこで見つかればよいという動き方です。Base は I から m() を継承しているので、Base のメソッドとして存在します。間にクラスが1枚挟まっていれば届きます。

判定手順。super.m() を見たら ──
① extends を書いているか。書いていなければスーパークラスは Object
② その親クラスが m() を持っているか（自分で定義／継承のどちらでも可）

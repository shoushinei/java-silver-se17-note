Object から受け継ぐ toString / equals / hashCode

extends を書かないクラスは、暗黙に java.lang.Object を継承しています。つまりすべてのクラスが、Object のメソッドを最初から持っています。その中で試験に出るのが次の3つです。

メソッドObject の既定の動作オーバーライドする目的
toString()クラス名@16進のハッシュ値中身を読める文字列にする
equals(Object)参照の比較（== と同じ）中身で等しいかを判定する
hashCode()オブジェクトごとの値equals と矛盾しない値にする

3つとも「オーバーライドされる前提」で用意された仮の実装です。Object は、あなたのクラスの「中身」が何なのかを知りません。だから文字列にするときは型の名前と識別用の番号しか出せず、比べるときは「同じインスタンスかどうか」しか判定できません。

println はオブジェクトを受け取ると toString() を呼ぶ

println(Object) がしていること最重要
// System.out.println(x) は、おおむね次のように動く
String s = (x == null) ? "null" : x.toString();   // String.valueOf(x) と同じ
// → s を出力する

ポイントは2つです。null のときは toString() を呼ばずに "null" と表示するので、例外になりません。null でなければ、そのオブジェクトの toString() が呼ばれます。オーバーライドしていれば自分の実装、していなければ Object の既定の実装です。文字列連結の "値: " + x も同じ仕組みで toString() を呼び、null なら "値: null" になります。

反対に、null を確かめずにメソッドを呼んでしまうのが switch です。switch (s) は裏で s.hashCode() を呼ぶので、s が null なら NullPointerException になります（第3章 08）。

自作クラスで確かめる

toString() をオーバーライドしたクラスの配列最頻出
class Box {
    public String label;
    public Box(String label) { this.label = label; }
    public String toString() { return label; }       // オーバーライド
}

Box[] boxes = { new Box("X"), new Box("Y"), new Box("Z"), null };

System.out.println(boxes[1]);         // Y     ← Box の toString() が呼ばれる
System.out.println(boxes[2].label);   // Z     ← フィールドを直接出力
System.out.println(boxes[3]);         // null  ← null なので toString() は呼ばれない

ハッシュ値が出るのは toString() をオーバーライドしていないときだけです。この例では Box がオーバーライドしているので、boxes[1] は Box@7344699f のような形にはなりません。
また、boxes[3] は null ですが、println に渡しただけなら例外にならず "null" と出ます。「null なので実行時に例外」を選ばせる引っかけに注意してください。

null に「ドット」を付けた瞬間に例外対比
System.out.println(boxes[3].label);        // NullPointerException
System.out.println(boxes[3].toString());   // NullPointerException

println 自身は null を確かめてから toString() を呼びます。しかし boxes[3].label や boxes[3].toString() は、println に渡す前に自分で null をたどってしまうので例外になります。第2章 13「null との付き合い方」と同じ判定です。

なぜハッシュ値になるのか

Object の toString() の正体OK
class Plain { }                  // toString() をオーバーライドしていない

Plain p = new Plain();
System.out.println(p);           // Plain@18b4aac2

// Object の toString() は、次の文字列を作っているだけ
p.getClass().getName() + "@" + Integer.toHexString(p.hashCode());   // Plain@18b4aac2

@ の後ろは hashCode() の値を16進数で書いたものです。実行するたびに変わるので、選択肢に出てくる @7344699f のような数字そのものに意味はありません。「この形になるかどうか」だけを判定してください。

配列も同じです。配列は toString() をオーバーライドしていないので、int[] なら [I@...、String[] なら [Ljava.lang.String;@... になります。記号の読み方は第2章 11「配列」にあります。

ハッシュ値にしない方法

対象中身を表示する方法
自作クラスpublic String toString() をオーバーライドする
配列Arrays.toString(配列)。2次元なら Arrays.deepToString
ArrayList などのコレクションそのままで [a, b] と出る（オーバーライド済み）
String / StringBuilder / ラッパークラスそのままで中身が出る（オーバーライド済み）
recordそのままで Point[x=1, y=2] と出る（自動生成。第4章 10）
入れ物と中身は別々に判定する要注意
System.out.println(List.of(new Box("X"), new Box("Y")));   // [X, Y]
System.out.println(List.of(new Plain()));                  // [Plain@...]
System.out.println(Arrays.toString(boxes));                // [X, Y, Z, null]

リストや Arrays.toString は、各要素の toString() を呼んで [ ] でつないでいるだけです。要素のクラスがオーバーライドしていなければ、中身はハッシュ形式のままです。

toString() のオーバーライドでよくある誤り

3つともコンパイルエラー頻出
class A { String toString() { return "a"; } }
// error: attempting to assign weaker access privileges; was public

class B { public void toString() { } }
// error: return type void is not compatible with String

class C { @Override public String tostring() { return "c"; } }
// error: method does not override or implement a method from a supertype

public を付け忘れると、アクセスを狭めたことになってコンパイルエラーです。Object の toString() が public なので、オーバーライドする側も public 以外は書けません（第5章 12 の「狭めるのは不可」）。
C のように綴りを間違えた場合、@Override が無ければコンパイルは通ります。ただしそれは新しい別メソッドなので、println するとハッシュ値が出ます。

null を直接渡すと、どのオーバーロードか決まらない要注意
System.out.println(null);            // コンパイルエラー
// error: reference to println is ambiguous
//   println(char[]) と println(String) の両方が当てはまる

System.out.println((Object) null);   // OK。"null" と出る

String 型や Object 型の変数に入った null なら "null" と出ます。null と直接書いたときだけ、どのオーバーロードを呼ぶか決められずにエラーになります。
ただし char[] c = null; を println(c) すると、char[] 専用のオーバーロードが中身を読みに行くので NullPointerException です。

equals() ── オーバーライドとオーバーロードの取り違え

引数の型が Object でなければオーバーライドではない最頻出
class P {
    int x;
    P(int x) { this.x = x; }
    public boolean equals(P o) { return x == o.x; }   // 引数が P ＝ オーバーロード
}

P a = new P(1), b = new P(1);
Object o = b;

a.equals(b);              // true  ← equals(P) が選ばれる
a.equals(o);              // false ← equals(Object) ＝ Object の参照比較が選ばれる
List.of(a).contains(b);   // false ← コレクションは equals(Object) を呼ぶ

Object の equals は引数が Object 型です。equals(P o) と書くと引数リストが違うのでオーバーライドではなくオーバーロードになり、Object の equals(Object) は残ったままです。どちらが呼ばれるかは引数の宣言型で決まるので、Object o を渡すと参照比較になります。@Override を付ければ、コンパイルエラーで気付けます。

正しいオーバーライドの形OK
@Override
public boolean equals(Object o) {                   // 引数は Object
    return o instanceof P p && x == p.x;            // 型を確かめてから比べる
}

hashCode() ── equals を変えたら一緒に変える

決まりは1つだけです。equals で等しいと判定される2つのオブジェクトは、hashCode() も同じ値を返さなければなりません。HashSet や HashMap は、まず hashCode() で候補を絞ってから equals で比べるためです。

equals だけ変えると、HashSet が重複を見抜けない要注意
class Q {        // equals(Object) だけオーバーライド
    ...
}
Set<Q> qs = new HashSet<>();
qs.add(new Q(1));
qs.add(new Q(1));
qs.size();       // 2 ← 既定の hashCode はインスタンスごとに違うので、
                 //     equals で比べる段階まで進まない

class R {        // equals(Object) と hashCode() の両方をオーバーライド
    ...
    @Override public int hashCode() { return Integer.hashCode(x); }
}
// 同じように2回 add すると size() は 1

逆向きは成り立たなくて構いません。hashCode が同じでも equals が false ということはあり得ます（別の中身が、たまたま同じ値になる）。「hashCode が等しいなら equals も true」という選択肢は誤りです。

まとめ

Object が全クラスに与える3つ暗記
toString()   既定は「クラス名@16進ハッシュ値」
equals()     既定は参照比較（==）
hashCode()   既定はオブジェクトごとの値

→ どれもオーバーライドされる前提で用意されている
→ println はオブジェクトを受け取ると toString() を呼ぶ
→ null のときは toString() を呼ばず "null" と表示する

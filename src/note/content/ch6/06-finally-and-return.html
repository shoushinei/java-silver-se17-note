finally と return ── この章の山場

黒本の章末で最も差がつくのがここです。ルールを3段階に分けます。

原則 ── finally は必ず実行される

return があっても finally は動く出力あり
int m() {
    try {
        return 1;
    } finally {
        System.out.println("finally");   // 実行される
    }
}
// "finally" が出力されたあと、1 が返る

罠1 ── return の値は finally より前に確定する

戻り値は 0（100 ではない）要注意
int m() {
    int val = 0;
    try {
        return val;      // ここで「0」が退避される
    } finally {
        val = 100;       // 退避済みの値には影響しない
    }
}
// 戻り値は 0

return val; の時点で val の値がコピーされて退避されます。その後 finally で val を書き換えても、退避された値は変わりません。

罠2 ── finally の return は上書きする

戻り値は 2要注意
int m() {
    try {
        return 1;
    } finally {
        return 2;        // こちらが最終的な戻り値
    }
}
// 戻り値は 2

罠3 ── finally の return は例外すら握りつぶす

例外は消える。戻り値は 2最重要
int m() {
    try {
        throw new RuntimeException();
    } finally {
        return 2;        // 例外がもみ消される
    }
}
// 例外はスローされず、2 が返る

選択肢に「実行時に例外がスローされる」があると、つい選びたくなります。finally に return があるなら例外は外に出ません。実務では絶対に書いてはいけないコードですが、試験には出ます。

finally が実行されない唯一のケース

System.exit で JVM ごと終了例外的
try {
    System.exit(0);
} finally {
    System.out.println("これは出ない");
}

第4章（値渡し）とつながります。return val で「値がコピーされる」のは、メソッド呼び出しで引数がコピーされるのと同じ仕組みです。Java は基本データ型を必ずコピーで扱う、という一貫した性質の別の現れ方だと考えると覚えやすくなります。
